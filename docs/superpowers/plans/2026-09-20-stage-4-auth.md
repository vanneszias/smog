# Stage 4: Auth — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People can create an account, sign in with a password or with Google, and reach account pages — and the favorites they built as a guest follow them in.

**Architecture:** Payload's own auth on the `users` collection, with a custom `AuthStrategy` for Google OAuth. Every server entry point that touches Payload is a `page.tsx` or a Payload **endpoint behind a rewrite** — never an `app/**/route.ts`, because that costs ~519 KiB of a 769 KiB budget. WorkOS is deleted, not ported.

**Tech Stack:** Payload 3.89.0 auth, Next.js 16 App Router, `@smog/ui-web`, Playwright.

**Spec:** [`../specs/2026-09-19-payload-migration-design.md`](../specs/2026-09-19-payload-migration-design.md)

## Global Constraints

Inherits all Stage 0–3 global constraints. Additionally:

- **Payload is pinned at `3.89.0`.** 3.90.x raises PBKDF2 to 600,000 iterations and workerd caps at 100,000. This is an *auth-path* constraint now — see "The password hashing problem" below.
- **No `app/**/route.ts` that imports Payload.** It becomes its own bundle entry and re-bundles the Payload/D1/drizzle graph: measured at **+519 KiB gzipped**. A `page.tsx` is free. OAuth callbacks go in `apps/site/src/endpoints/` behind a `next.config.ts` rewrite — Stage 3 Task 9 proved the pattern at +5 KiB.
- **There are no transactions on any write path.** The D1 adapter takes `defaultBeginTransaction()`, which returns `() => Promise.resolve(null)`, so nothing rolls back. Every multi-step write must be idempotent or ordered with the irreversible step last.
- **Deleting a user cascades their lists** (Stage 3 Task 8) and **nulls their consents** (Stage 1). Account deletion must honour both.
- **Access filters must never return `{ equals: undefined }`.**
- **The Worker budget is 10 MiB gzipped; CI warns at 8 MiB.** Entering this stage: 7,428.58 KiB (72.5%), so **~763 KiB of headroom**. Measure every task.
- **`bun release:check` is the gate**, and `site-e2e` now runs in CI too.

## The password hashing problem

Read this before Task 1, because it constrains the whole stage and it is not fixable here.

`payload/dist/auth/strategies/local/generatePasswordSaltHash.js` hashes with
**PBKDF2-HMAC-SHA256 at 25,000 iterations**. OWASP's current guidance for that
algorithm is 600,000. Payload 3.90.x raises it to exactly 600,000 — and that is
the release this project cannot run, because workerd caps PBKDF2 at 100,000
iterations (Stage 1 established this; it is why we are pinned).

So: **we are pinned to a version whose password hashing is roughly 24× weaker
than current guidance, by a platform limit that also forbids the fixed
version.** Payload does not expose the iteration count as configuration.

This does not block the stage, and it is not a reason to invent our own
password storage — a bespoke KDF is how you get something worse. It does change
what the stage should emphasise:

- **Social login is the preferred path**, not a nice-to-have. A Google account
  has no password for us to hash.
- **Configure lockout.** Payload supports `maxLoginAttempts` and `lockTime`;
  both default to off. Brute-force resistance has to come from rate limiting
  rather than from the KDF.
- **Record it**, so nobody later assumes the defaults are fine. Task 1 writes
  it into the collection and the findings doc.

Revisit when either Payload makes iterations configurable or workerd raises the
cap. Do not quietly upgrade Payload to "fix" it — that breaks the deploy.

## Review Focus

Five failure modes the spec implies that no happy-path test would catch:

1. **A session cookie that does not apply to the page you land on.** Every URL is locale-prefixed (`/nl/...`, `/en/...`). A cookie scoped to the path it was set from signs you out when you switch language. Task 2 tests that a session established under one locale is honoured under another.
2. **A guest-to-account favorites merge that loses or duplicates.** The merge is a multi-step write and **nothing rolls back**. It must be idempotent — running it twice is the normal case, because a second sign-in on the same browser still has the local array. Task 6 tests re-running it, a partial failure, and a gesture already favourited on the account.
3. **An OAuth callback that does not verify `state`.** A missing check is invisible to every happy-path test and is a login-CSRF. Task 3 tests a callback with a forged, absent and replayed `state`.
4. **Account deletion that fails on a foreign key, or takes the consents with it.** Deleting a user cascades their lists by design, but `user_consents` is nullable *specifically so the record survives the account* — that is a legal-retention requirement from the spec. Task 5 deletes a real user with lists and consents and asserts both outcomes.
5. **Email enumeration.** Sign-up, sign-in and password reset must not reveal whether an address is registered — same response, same timing class. Task 2 tests that the responses are indistinguishable.

### Task 1: Harden the users collection, and record what cannot be hardened

**Files:**

- Create: `apps/site/src/collections/Users.lockout.int.test.ts`
- Modify: `docs/superpowers/specs/2026-09-19-stage-0-findings.md`

**Interfaces:**
- Consumes: the `users` collection from Stage 1.
- Produces: `maxLoginAttempts` and `lockTime` on `users.auth`; a documented password policy.

- [ ] **Step 1: Write the failing lockout test**

Against a real database: after N failed sign-ins the account locks, and a *correct* password is then also refused until the lock expires. The second half is the one that matters — a test that only checks the wrong password keeps failing passes against no lockout at all.

```ts
it("locks the account after repeated failures", async () => { /* ... */ });
it("refuses the correct password while locked", async () => { /* ... */ });
it("does not lock a different account", async () => { /* ... */ });
```

- [ ] **Step 2: Run it to verify it fails**

**This step's premise was wrong and the correction is kept here deliberately.**
Payload 3.89.0 does *not* default lockout to off: `addDefaultsToAuthConfig`
(`collections/config/defaults.js:138-140`) applies `lockTime: 600000` and
`maxLoginAttempts: 5` even to a bare `auth: true`, and `sanitize.js:218` runs
it for the boolean form. All three lockout tests passed on their first run.

Writing the values out explicitly is still worth doing — an upstream default
moves silently under a dependency bump, and an edit that expands `auth` is one
forgotten key away from `maxLoginAttempts: 0` — but it changed no behaviour on
the day, and the commit says so.

- [ ] **Step 3: Configure lockout**

`maxLoginAttempts: 5`, `lockTime: 10 * 60 * 1000`. Verify at the call site in `node_modules/payload/dist/auth/` what units `lockTime` takes and whether the counter resets on success — do not assume.

- [ ] **Step 4: Password policy**

Payload validates password presence, not strength. Add a `validate` on the password field with a minimum length of 12 and a rejection of the obvious top-N passwords, and test that a 200-character password is *accepted* — an upper bound is a denial-of-service on a slow KDF, but 25,000 iterations is cheap and an arbitrary cap frustrates password managers.

- [ ] **Step 5: Record the hashing limitation**

Append to the findings doc: the 25,000-iteration measurement, the workerd cap, why the fixed version cannot be used, and the mitigations chosen. Anyone reading `Users.ts` later must find the reason in the file too, not just here.

- [ ] **Step 6: Mutation-prove and commit**

**Not by removing `maxLoginAttempts`** — that hands the decision back to the
default, which puts 5 back, so only the config-shape test notices and the
behavioural one stays green. Verified.

Mutate `lockTime` to `0` (the lock expires the instant it is set) or
`maxLoginAttempts` to `50`. Both fail `refuses the correct password while
locked` and `locks the account after repeated failures` by name.

Avoid `maxLoginAttempts: 0`: `getBaseAuthFields` only adds the `loginAttempts`
and `lockUntil` columns when it is greater than zero, so that is a schema
change and `pushDevSchema` will drop columns out of the shared local D1
mid-sweep.

- [ ] **Step 1: Write the failing cookie-scope test — Review Focus item 1**

```ts
it("honours a session established under /nl when the visitor moves to /en", async () => { /* ... */ });
```

Sign in under one locale in a browser test, navigate to another, assert the account nav still shows. A cookie with a path of `/nl` passes every single-locale test and fails this one.

- [ ] **Step 2: Write the enumeration tests — Review Focus item 5**

Task 1 found the concrete leak, verified against a real database. All three
cases return 401, but not the same one:

| case | error class | body |
|---|---|---|
| unknown address | `AuthenticationError` | "The email or password provided is incorrect." |
| wrong password | `AuthenticationError` | identical — good |
| **locked account**, wrong *or correct* password | `LockedAuth` | "This user is locked due to having too many failed login attempts." |

An unregistered address never locks, so seeing that message proves the account
exists. **The sign-in endpoint must flatten `LockedAuth` into the
`AuthenticationError` body.**

There is a timing half too: `checkLoginPermission` runs *before*
`authenticateLocalStrategy`, so unknown and locked both answer without touching
PBKDF2, while a wrong password on a live account pays 25,000 iterations. Decide
what to do about that here — it is this task's latency budget — and if you
choose not to equalise, say why with the measured difference.


Sign-up with an address that already exists, and sign-in with one that does not, must be indistinguishable from the negative case in status code and body. Assert the *exact* response, not just that it failed.

Payload's default `Forbidden` / duplicate-key errors do leak this. Expect Step 1 to fail and to need an explicit shape.

- [ ] **Step 3: Implement the endpoints**, then the pages, then `readSession`.

`readSession` reads the Payload cookie from `headers()` and calls `payload.auth`. Stage 3 Task 5 built `fetchViewer` for this and then deleted it when a mutation proved it dead on that page — read that history before rebuilding it; here it is genuinely needed, and the difference is worth understanding.

- [ ] **Step 4: Measure the bundle, then commit.**

### Task 7: Lists become owned

**Files:**
- Create: `apps/site/src/app/(frontend)/[locale]/account/lists/page.tsx` and `account/lists/[id]/page.tsx`
- Modify: `apps/site/src/collections/Lists.ts` if minting needs an owner path

**Correction to Task 7's file list, found before starting it.**

The plan says:

> - Create: `apps/site/src/app/(frontend)/[locale]/lists/page.tsx` and `[id]/page.tsx`

`[id]/page.tsx` cannot be created there. Stage 3 Task 7 already shipped
`app/(frontend)/[locale]/lists/[shareToken]/page.tsx`, and Next.js refuses two
different slug names on the same segment. From Next's own router
(`shared/lib/router/utils/sorted-routes.js`):

```
You cannot use different slug names for the same dynamic path
('${previousSlug}' !== '${nextSlug}').
```

This is a build-time throw, not a warning, so the app would not start.

**Resolution: the owner's surface moves under `/account`.**

- `app/(frontend)/[locale]/account/lists/page.tsx` — the owner's index
- `app/(frontend)/[locale]/account/lists/[id]/page.tsx` — one owned list
- `app/(frontend)/[locale]/lists/[shareToken]/page.tsx` — unchanged, public

Not just a workaround for the router. The two surfaces answer to different
access rules and different audiences: `[shareToken]` is an unauthenticated
capability URL that `access/shareTokens.ts` resolves, and the owner's pages
are `isListOwner` reads behind a session. Putting them at sibling paths under
one segment was always going to invite one to be mistaken for the other — the
same reasoning that split `/account/confirm-email` from `/account/email` in
Task 5. `/account/*` already means "signed in, yours"; the rewrites and
`AccountNav` are there.

The rest of Task 7 stands unchanged, including **use the Stage 3 access rules,
do not rewrite them**, and re-run their mutation sweep with a UI in front.


Create, rename, delete, add and remove gestures, share and un-share. The access rules and rotation already exist from Stage 3 Task 7 and are mutation-proven — **use them, do not rewrite them**, and re-run their mutations afterwards to prove they still bite with a UI in front.

## Stage 4 exit criteria

1. A visitor can create an account with an email and password, sign in, and sign out.
2. A visitor can sign in with Google, and an existing password account with the same *verified* email is linked rather than duplicated.
3. A session survives a locale switch.
4. Repeated failed sign-ins lock the account, and the lock refuses a correct password.
5. Sign-up, sign-in and reset do not reveal whether an address is registered.
6. Guest favorites merge into the account on first sign-in, idempotently.
7. Account pages allow password change, email change and account deletion; deletion removes the user's lists and keeps their consent record with a null user.
8. Nothing under `apps/site` imports `@smog/auth` or reaches WorkOS, enforced by a test. (`packages/auth` itself survives until Stage 10 — four other packages still import it.)
9. The bundle is measured and recorded, and no `app/**/route.ts` imports Payload.
